## r59 探针结论（21:44 日志）：不是权限不够，是另外两条规矩

`READ_WRITE_USER_FILE` **确实生效了**，只是生效范围比预想的窄：

| 对象 | 结果 | 说明 |
|---|---|---|
| `home` / `.harmonybrew` / `bin` | ✅ 可读 | 目录枚举正常（539 项） |
| **`Homebrew/bin/brew`（真实文件）** | ✅ **open 成功**，头两行 `#!/usr/bin/zsh -pu` | 普通文件可读 |
| **`Cellar/node/.../node`（真实文件）** | ✅ **open 成功**（ELF 头正常） | 普通文件可读 |
| `~/.npmrc` | ✅ 可读 | `prefix=/storage/Users/currentUser/.harmonybrew` |
| **`bin/brew`、`bin/node`（symlink）** | ❌ `lstat` / `realpath` / `open` 全 `EACCES` | **沙箱不允许跟随符号链接** |
| `/usr/bin/zsh` | ❌ `ENOENT` | **应用命名空间里没有这个路径** |
| `spawn` 真实 node | ❌ `EPERM` | **ELF 签名策略**：harmonybrew 的 node 是 `self-sign`，只有本应用证书签的 ELF 才能 exec |
| `spawn` 真实 brew 脚本 | ❌ `ENOENT` | shebang 是 `#!/usr/bin/zsh -pu`，而 zsh 在应用命名空间里不可见 |

所以"不是这个权限，而是别的"——**是两条平台策略**：

1. **符号链接跨不过去**（`~/.harmonybrew/bin/*` 全是 symlink 指向 `Cellar` / `Homebrew`），
   所以要读文件必须自己走 `Homebrew/bin/...`、`Cellar/...` 这类**真实路径**；
2. **exec 只认本应用证书签名**（这条 r47 就记录过：自签 ELF → `EPERM`），
   所以**永远不可能**从 Motrix 里直接跑用户的 `brew` / `node` / `npm`。

## r60 还要确认两件事

1. **能不能写**：CLI 集成的现实做法是"往用户 PATH 里写一个 shell 垫片脚本"，
   用户在自己的终端里跑它（用户域的 shell 有 zsh 和 brew，不受我们签名限制）。
   所以必须确认应用能否在 `~`、`~/.harmonybrew/bin`、`~/npm/bin` 下**建/删文件**。
   r60 新增 `userFile.write.*`（write / cleanup 各自带 errno）。
2. **应用命名空间里到底有哪些 shell**：r60 新增 `userFile.shells`，
   逐个 `fileProbe` `/bin/sh`、`/bin/bash`、`/bin/zsh`、`/usr/bin/*`、`/system/bin/sh`，
   决定垫片脚本的 shebang 该写什么。

另外 `userFile.installed.*` 会把 formula / npm 包 / 命令名**全量**列出来（各最多 200 项），
这就是集成卡片里"已安装工具"列表的数据源。
