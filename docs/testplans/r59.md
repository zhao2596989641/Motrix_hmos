## r58 aclprobe 真机结果（20:11 日志）

`READ_WRITE_USER_FILE` 的 ACL 确实生效了，但只到"目录可读"这一层：

| 探针 | 结果 |
|---|---|
| `userFile.home` | ✅ `exists:true, count:170`（能看到 `.bailian` / `.bitfun` / `.bun-*.so`…） |
| `userFile.harmonybrew` | ✅ `exists:true, count:12` |
| `userFile.harmonybrewBin` | ✅ `exists:true, count:539` |
| `brewScript`（symlink） | ❌ `EACCES` |
| `brewNode`（symlink） | ❌ `EACCES` |
| `/usr/bin/zsh` | ❌ `ENOENT` |
| spawn brew/node | 仍 `EACCES` / `status 127` |

也就是说：**目录能列出来，但 symlink 指向的文件 `stat/open` 被拒**。这可能是
（a）沙箱对 symlink 的额外限制，或（b）文件本身的访问控制（owner/group/mode/SELinux label）问题。

## r59 探针要回答什么

`cli-probe.json` 的 `userFile` 新增：

- `link.brewScript` / `link.brewNode` / `link.brewReal` / `link.nodeReal` / `link.npmrc`：
  分别输出 `lstat`、`readlink`、`realpath`、`open` 四组结果（各自带 errno 与前 2 行内容）；
- `groups` / `uid` / `gid`：确认应用进程到底在不在 `file_manager` 组（文件是 770 file_manager）；
- spawn 增加**真实路径**（绕过 symlink）：
  `brewNodeReal`（`Cellar/node/26.12.0/bin/node`）、`brewReal`、`brewRealViaSh`。

判读：

- `link.brewReal.open.ok=true` ⇒ 文件可读，之前只是 symlink 被拦 ⇒ **CLI 检测可行**（用 realpath），
  但 exec 还要看 `spawn.brewNodeReal` 是否 ok；
- 所有 `open` 都 EACCES ⇒ `READ_WRITE_USER_FILE` 只放开目录/遍历，文件仍受 SELinux 保护 ⇒
  CLI 只能做「复制安装命令」，不能软件内直接调；
- `groups` 不含 1006 而目录能读 ⇒ 权限走的是 SELinux/ACL 而不是 group 位，文件 770 的 group 位
  正好解释 `EACCES`——那就可以考虑让用户把 harmonybrew 的 bin 文件 chmod 755（或复制到 app 可读目录）
  作为 workaround（仍受 exec 策略限制）。
