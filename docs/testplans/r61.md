## BitFun 是怎么做到的（读它的源码得到的结论）

它的实现分三块，在 `src/crates/interfaces/acp/src/client/managed_provisioning.rs` 与
`src/crates/services/services-core/src/system/command.rs`：

1. **检测**：`which` + 把登录 shell 的 PATH 合并进来；鸿蒙上它会 `sh -c '. ~/.zshrc; printf $PATH'`，
   还会**直接读 `.zshrc` 文本**，从 `brew shellenv` 那行反推 `HOMEBREW_PREFIX/bin`（因为登录 shell
   可能因为 `set -e` 提前退出）。
2. **安装**：**真的 spawn** `/storage/Users/currentUser/.harmonybrew/bin/brew` 或
   `.../bin/node <npm-cli.js> install -g --prefix <harmonybrew>`，环境固定成
   `HOME=/storage/Users/currentUser`、`HOMEBREW_PREFIX=.../.harmonybrew`、`PATH=.harmonybrew/bin:/system/bin`。
3. **运行**：ACP client 直接 exec 装好的 CLI。

它还额外声明了 `ohos.permission.CUSTOM_SANDBOX`（"访问自定义沙箱路径"）与 `READ_WRITE_USB_DEV`，
数据目录放在 `~/.bitfun`（我们确认过这个目录存在）—— 也就是**动态沙箱**形态。

**我们的差别**：同在 `apl=normal / hos_normal_app`，但我们的进程域是 `u:r:debug_hap:s0`，
BitFun 很可能跑在更宽的开发工具域（我们自己的 DSHM 沙箱就是 `u:r:develop_tools_debug_hap:s0`，
在那个域里自签 ELF **可以** exec）。差别最可能来自 `CUSTOM_SANDBOX`（动态沙箱 → 换域）。

**想验证的话**：把 `CUSTOM_SANDBOX` 也声明进清单（排在 `READ_WRITE_USER_FILE` 后面），
在 DevEco 重新自动签名，我解 profile 看 ACL 是否下发；若下发，再出探针包测 exec 是否变通。
但官方文档写明该权限"面向华为内部开发工具应用开放"，Motrix 作为下载器大概率批不下来 ——
所以 r61 先按"不依赖它"的方案做（检测 + 手动安装命令）。
