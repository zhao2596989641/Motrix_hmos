## 为什么试这条

r59/r60 真机探针确认：`READ_WRITE_USER_FILE` 只解决**读写**，
执行用户自签 ELF（`~/.harmonybrew/bin/node`）仍是 `EPERM`，brew 脚本则因
`/usr/bin/zsh` 不在应用命名空间而 `ENOENT`。

而 BitFun 能真的 `spawn ~/.harmonybrew/bin/brew install ...`，它比我们多声明的权限里，
最关键的是：

```
ohos.permission.CUSTOM_SANDBOX   // 允许应用把沙箱改为"动态沙箱"
```

我们的 DSHM 沙箱（`u:r:develop_tools_debug_hap:s0`）里**自签 ELF 可以 exec**，
而 Motrix 跑在 `u:r:debug_hap:s0`。怀疑动态沙箱会换到更宽的域，
所以先只做"声明 + 重新签名 + 看 ACL 有没有下发"这一步，成本最低。

## 本轮做了什么

1. `module.json5` 新增标记块（**已解注**，供签名时申请 ACL）：

   ```
   // >>> MOTRIX_CUSTOM_SANDBOX_PERMISSION_BEGIN
   { "name": "ohos.permission.CUSTOM_SANDBOX",
   "reason": "$string:perm_custom_sandbox_reason",
   "usedScene": { "abilities": ["EntryAbility"], "when": "always" } }
   // <<< MOTRIX_CUSTOM_SANDBOX_PERMISSION_END
   ```

2. `scripts/patch-module-permissions.mjs` 支持第三块：`custom-sandbox`
   （`status` / `enable|disable [jit|user-file|custom-sandbox|all]`，已做 enables↔disable 回环校验）；
3. `string.json` 增加申请理由（动态沙箱 / 用户目录 / 调用 Harmonybrew 工具）；
4. `docs/BUILD.md` 权限表补一行。
